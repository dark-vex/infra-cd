# Terraform — Conventions & Recipes

## Conventions

- **State backend:** Terraform Cloud (`Fastnetserv` org) for all stacks **except** `terraform/netbox/`, which uses S3 (Cloudflare R2 — `terraform-state` bucket, `auto` region). Migrated in PR #1404.
- **Required providers:** Hetzner Cloud, OCI, Proxmox (`~> 0.100`), 1Password (`~> 3`)
- **Format:** Always run `terraform fmt` before committing — CI rejects unformatted files
- Each `terraform/{environment}/` (or `terraform/proxmox/{host}/`) is independent with its own backend config
- Reusable modules published as standalone repos: `dark-vex/terraform-proxmox-vm`, `dark-vex/terraform-proxmox-lxc`, `dark-vex/terraform-hetzner-server`, `dark-vex/terraform-cloudflare-dns`, `dark-vex/terraform-cloudflare-tunnel` — referenced via `github.com/dark-vex/<name>?ref=<commit-sha>  # vX.Y.Z` (SHA-pinned for supply-chain safety; the trailing comment records the tag the SHA corresponds to)
- **Renovate visibility for the SHA-pinned module convention above (CODE-53):** the native `terraform` manager extracts these as `depType: "module"` but sets `currentValue` to the raw SHA, which `versioning: "semver-coerced"` can't turn into a comparable version — so it silently proposes zero updates regardless of how far behind the pin is (confirmed via `renovate.yml` `workflow_dispatch` debug dry-run, root-caused against Renovate's own source: `pinDigests` doesn't apply to Terraform Git-module sources, deliberately disabled after it broke Git-module updates upstream, renovatebot/renovate#15113). Fixed by a `customManagers` regex entry (`.renovate/customManagers.json5`) that reads the SHA into `currentDigest` and the trailing comment into `currentValue`, datasource `github-tags` — with the native terraform-manager extraction disabled for `dark-vex/terraform-*` packages (`.renovate/terraform.json5`) so there's exactly one manager per dep. **This only works if the `# vX.Y.Z` comment sits on the same line, immediately after the closing quote of `ref=<sha>"`, with the `v` prefix intact** — the regex is `source\s*=\s*"github\.com/(dark-vex/terraform-[a-z-]+)\?ref=([a-f0-9]{40})"\s*#\s*(v[0-9.]+)`. Any other formatting (comment on its own line, missing `v`, a differently-shaped module name) makes Renovate silently blind to that occurrence again, with no error or warning anywhere.
- **Non-registry Terraform providers** (a compiled Go binary, not a module — the module SHA-pinning convention above doesn't apply): `terraform/hostbrr/` consumes `dark-vex/terraform-provider-virtfusion` (CODE-27), which is not published to the public Terraform Registry. Pinned via Terraform's `filesystem_mirror` provider-installation method fed by a pinned, checksum-verified, not-rebuilt-per-run release binary — never `dev_overrides` (bypasses `.terraform.lock.hcl` checksum verification entirely). `.terraform.lock.hcl` is generated locally, once, via `terraform providers lock -fs-mirror=<dir> -platform=linux_amd64 -platform=darwin_arm64` against real downloaded+checksum-verified release zips (covering both the self-hosted runner's platform and local dev on a Mac), and committed — never regenerated in CI. `required_providers` still uses `source = "registry.terraform.io/dark-vex/virtfusion"` (the mirror's implied source address) with a hand-pinned exact `version` (Renovate can't see a non-registry provider, so this is exempt from the "Renovate owns versions" rule). CI (`terraform-hostbrr.yml`) downloads the same pinned release zip into `$RUNNER_TEMP` and points `TF_CLI_CONFIG_FILE` at a `filesystem_mirror` config scoped to `$RUNNER_TEMP` — never appended to `~/.terraformrc`, which is shared by every other Terraform workflow on the same persistent self-hosted runner. TFC auth flows via the `TF_TOKEN_app_terraform_io` env var, not `cli_config_credentials_token`, for the same reason. Rejected alternatives: publishing to the public/a private Terraform Registry, or standing up a `network_mirror`-protocol service — both disproportionate for one provider used by one stack; revisit only if a second consumer appears. `rmon_vpn`'s attributes (hostname, public IPv4/IPv6, MAC address) are real and computed, not schema-marked `sensitive` — CI never prints full `plan`/`apply` output for this stack (captured to a local log file, only the resource-count summary line surfaced), same pattern as `terraform/aws/`'s bucket-name leak fix. Keep it that way in any future edit to `terraform-hostbrr.yml`.
- **Local `terraform init` provider staleness (CODE-55, investigated, no CI fix needed):** every stack except `terraform/hostbrr/` and `terraform/backblaze/` gitignores `.terraform.lock.hcl`, but this is *not* a CI staleness risk — every Terraform workflow's `actions/checkout` runs with its default `clean: true` (unoverridden), which `git clean -ffdx`s the persistent self-hosted runner (wiping any prior `.terraform/`/lock file) before each checkout, so CI always re-resolves providers fresh regardless of whether `-upgrade` is passed. Confirmed via CI logs during the `e-breuninger/netbox` incident (PR #2057): the pre-fix failing run (`36164985482`, constraint still `~> 5.0`) resolved fresh to `v5.8.0` — not a stale cached `5.3.0` — and the post-fix passing run (`36165577930`, constraint tightened to `>= 5.6.1, ~> 5.8`) resolved to the *same* `v5.8.0`; the constraint change didn't change what CI installed, so provider staleness wasn't the CI-side cause of the incident (the exact trigger — a transient issue during NetBox Cloud's server-side rollout window vs. something else — was not conclusively established, but the logs rule out CI-side staleness as the mechanism). The real gap is **local-only**: a developer's own gitignored `.terraform.lock.hcl` never gets `git clean`'d between sessions, so a long-lived local checkout can silently keep an old locked provider version on disk. Run `terraform init -upgrade` before trusting a local plan on these stacks (never on `hostbrr`/`backblaze` — their lock file is deliberately committed and hand-pinned via `filesystem_mirror`, per the non-registry-provider note above; `-upgrade` would be actively wrong there).
- **Secrets provider by stack** (never hardcode sensitive values — source from the stack's provider(s) below):
  - **1Password only:** `terraform/hetzner/`,  `terraform/grafana/`, `terraform/oci/k8s-armchair/`, `terraform/oci/teleport/` (proxy hostname is a root-level custom field on the existing `teleport-server` item — not exposed via the standard `onepassword_item` data source, so it's read via a `data "external"` + Connect API script instead of `section_map`), `terraform/hostbrr/` (CODE-27 — dedicated item "Hostbrr API - Terraform" in the same vault as every other Terraform-consumed 1Password item, `66qfxcmgwlhutunx6slav6fyve`; the endpoint URL sits in an unlabeled section, read by iterating `section[].field[]` by label rather than `section_map`, same technique as `test_vpn`; no SOPS needed — `rmon-vpn`'s name is already public in NetBox/DNS)
  - **SOPS only** (`carlpett/sops`, age-encrypted `secrets.sops.yaml`): `terraform/DNS/`, `terraform/cloudflare-tunnel/`
  - **Both:** `terraform/authentik/` (Authentik SSO on kubenuc — foundation merged in #2145, then the four custom application+provider pairs imported; blueprint-owned default objects — flows, brand, stages, policies, default RBAC roles — are deliberately NOT managed because blueprints re-apply them on a schedule; 1Password for the API URL + service-account token from the item "Authentik Terraform", the bootstrap service account/role/group/token stay unmanaged so an RBAC apply cannot revoke its own access; SOPS for every FQDN-bearing provider attribute — OAuth2 redirect URIs, SAML ACS URL — and the OAuth2 client IDs, via `SOPS_AGE_KEY_AUTHENTIK`), `terraform/netbox/` (1Password for API credentials; SOPS for on-prem IP/prefix inventory), `terraform/proxmox/rabbit/`, `terraform/proxmox/gozzi-hpelvisor/`, `terraform/proxmox/ec200/`, `terraform/oci/test_vpn/` (1Password for Proxmox/API credentials + SSH keys; SOPS for VM/LXC/instance hostnames), `terraform/oci/ams_vpn/` (CODE-15 — separate OCI tenancy from the other `terraform/oci/*` stacks; own dedicated 1Password item "OCI AMS API Key" for provider credentials + SSH keys, same split reasoning as `test_vpn`; SOPS for the instance hostname), `terraform/aws/` (CODE-20 — merged and applied 2026-09-15, PR #1982; all 3 buckets under management via `import {}`, zero drift confirmed post-apply; 1Password for AWS API credentials, SOPS for bucket names that would otherwise reintroduce a brand string this repo already purged from its history — same rationale as the Proxmox stacks' hostname handling), `terraform/backblaze/` (CODE-20; 1Password for the B2 application key, SOPS for the bucket name — same brand-string rationale as `terraform/aws/`. Known gap: the 1Password item's own title, "Backblaze Nextcloud-Fastnetserv bucket", still embeds that brand string in `data.tf` — rename the item to something generic, or switch the data source to `uuid` lookup, before treating this stack as fully clean), `terraform/portainer/` (Portainer's own configuration — adoption complete, #2137-#2141; 1Password for the API key/URL/Cloudflare Access service token in "Portainer-Terraform" and for the registry credentials in "Portainer-Registry-Harbor"/"Portainer-Registry-DockerHub"; SOPS for the FQDN-bearing environment name/address/public IP and the Harbor registry name/URL — see the "Portainer" section below), `terraform/auth0/` (import of the existing live Auth0 tenant, staged adoption — 1Password for the M2M app's domain/client ID/client secret bootstrap auth; SOPS for every FQDN-bearing resource attribute — per-client `callbacks`/`allowed_logout_urls`/`web_origins`/`initiate_login_uri`, `auth0_tenant.default_redirection_uri`, any `auth0_custom_domain.domain` — since these are whole-list authoritative values generated verbatim by `auth0 tf generate`, not just credentials like the other 1Password-only stacks)
  - Each SOPS-using stack has its own dedicated age keypair and `SOPS_AGE_KEY_*` GitHub Actions secret — never shared across stacks
- **`terraform/auth0/` — import+sensitive-value plan quirk (found during the remaining-clients PR, #2111):** the first time a resource's `import {}` block is adopted alongside a body that references a SOPS-sourced (auto-`sensitive`-marked) value, `terraform plan` shows that resource as "to change" even when the value is byte-identical to live — reproduced in isolation by wrapping an otherwise-unchanged literal in `sensitive(...)`, which alone produces the same spurious diff. This is a limitation of Terraform's *experimental* import+config-generation diffing (the "Config generation is experimental" warning), not a sign the generated config is wrong: confirmed by applying once (a no-op write, verified via a raw Management API read before/after showing no actual value change) and immediately re-planning, which came back `No changes`. **Expect this on every future adoption PR that introduces a SOPS-sourced field on a resource for the first time** — the zero-diff verification gate still applies, just one plan later (confirm via a second, post-apply plan rather than treating the first "N to change" as a failure to fix).
- Do not hand-pin provider versions managed by Renovate
- **`terraform/backblaze/` (CODE-20) — resolved 2026-09-23 via a fork, not upstream.** The official `Backblaze/b2` provider has a confirmed bug: `b2_bucket` Read returns `bucket_type`/`default_server_side_encryption` blank and an invalid `file_lock_configuration` shape for bucket-restricted application keys, root-caused to b2sdk's own bucket cache serving a stub object instead of a real API response (see `dark-vex/terraform-provider-b2#1`). Not fixed upstream, and deliberately not upstreamed — this stack pins `registry.terraform.io/dark-vex/b2` (our fork, release `v0.14.0-fix.1`) via the same checksum-verified `filesystem_mirror` pattern as `terraform/hostbrr/`'s non-registry-provider convention above. Live CI plan against the real `infra-cd-backblaze` TFC workspace now shows `Plan: 1 to import, 0 to add, 0 to change, 0 to destroy` — the first clean plan this stack has ever produced.
- **`local-exec`/`terraform_data` escape hatch** (precedent: the now-decommissioned `terraform/semaphore/main.tf`, see git history): only reach for this when a provider genuinely doesn't wrap a real, documented API endpoint (confirmed by checking the provider's schema/source, not assumed) — a custom provider is over-engineering for a couple of endpoints, and a manual out-of-band step violates this repo's no-config-drift convention. Make it idempotent (GET-then-match-then-PUT/POST, never a blind POST) and drive re-runs via `triggers_replace` hashing both the desired config and the helper script itself — `terraform_data` provisioners only fire on `create` otherwise. Document the known limitation plainly: this doesn't detect out-of-band drift on an otherwise-unchanged apply.

**CI workflow stages** (fmt → init → validate → plan-as-PR-comment → apply-on-main): see the `ci-workflows` skill's "Terraform CI workflow pattern" for the full step-by-step and copy-paste template — don't duplicate it here.

## Portainer (`terraform/portainer/`)

Manages Portainer's *own* configuration with the `portainer/portainer` provider (`>= 2.0.0, < 3.0.0`; the lockfile is gitignored, so the cap is explicit). The instance (Portainer BE 2.45.x, personal licence) manages **Docker agent hosts**, not Kubernetes — Flux still owns the cluster, so workload objects are out of scope.

**Managed (all via `import {}`, zero drift verified post-apply):** 2 tags, 3 endpoint groups (the built-in "Unassigned" group id 1 is referenced by literal id), 4 Docker agent environments (`environments.tf`, one `for_each`, `prevent_destroy`), 2 registries (`registries.tf`), and the settings singleton (`settings.tf`).

**Deliberately not managed:** users and teams (internal users need passwords Portainer cannot return — supplying one is a real rotation; the break-glass admin must stay outside Terraform), licence, S3/scheduled backup (`portainer_backup_s3` runs a backup on every apply), `portainer_auth` (logs in on every apply and stores a JWT in state), registry access (none exists), all stacks/Helm/`kubernetes_*`/edge/`docker_*` resources, and every one-shot action resource. `portainer_settings` OR `portainer_ldap_settings`, never both.

**Provider quirks found during adoption:**
- **Settings is import-only on purpose:** every `portainer_settings` attribute and nested block is optional+computed, so `settings.tf` sets nothing and the apply writes nothing. Pin values one at a time in follow-up PRs; do not add the `oauth_settings`/`ldap_settings` blocks without a break-glass login verified first (an update sends the whole settings object).
- **Environments:** the provider does not read `tls_*` on import and defaults all three to `true`, so the first apply wrote them to the live agents even when unset. `environments.tf` declares them explicitly (matching live) so that write is visible. Name/address/public IP show as `~ (sensitive value)` with "unchanged" on import — the same SOPS-sensitive artifact as `terraform/auth0/`.
- **Registries:** Portainer never returns the password, so the first apply writes it from the 1Password item. Portainer uses a Harbor *robot account* (read-only pull), not the Harbor admin login.
- **Transient apply failure:** the first environments apply failed with no visible error (counts-only CI log) but had already recorded the work in state; a plain CI re-run passed with `0 changed`. The live state was diffed against a pre-apply baseline and was identical.

**Execution:** the HCP workspace `infra-cd-portainer` runs in local mode on the self-hosted runner (so HCP has no run logs). The Portainer URL is published through a Cloudflare Tunnel behind Cloudflare Access; the provider sends the service token via `custom_headers`.

## Grafana Dashboards (`terraform/grafana/`)

`generate_dashboards.py` generates every Terraform-managed dashboard JSON under `dashboards/{cluster}/*.json` from Python — never hand-edit a `dashboards/*.json` file, the CI drift-guard (`terraform-grafana.yml`) regenerates and diffs it on every PR (`python3 generate_dashboards.py && git diff --exit-code dashboards/` — run this locally before every commit that touches the generator).

**Registry pattern:** the `APPS` dict (`{cluster: [(file_name, namespace, display_name, dashboard_type), ...]}`) lists every dashboard; the `builders` dict maps each `dashboard_type` string to a `lambda c, fn, ns, d, u: build_x(...)` that returns the dashboard JSON. `stable_uid(cluster, file_name)` derives a deterministic UID so re-running the generator never changes existing dashboards' UIDs. To add a new app: add an `APPS` entry, write a `build_x(...)` function, register it in `builders`.

**Two ways to build a dashboard:**
- **Hand-rolled** (`build_postgresql`, `build_teleport_agent`, `build_haproxy_ingress`, etc.): panels built directly from the shared helpers (`p_row`/`p_stat`/`p_ts`/`p_stat_multi`/`p_gauge`/`p_logs`, plus the composite `status_row`/`resource_row`/`reliability_row`). Use this when no suitable official/community dashboard exists, or the app's metric surface is small enough to hand-write.
- **Template import** (`build_harbor_from_template`, `build_awx_from_template`, `build_seaweedfs_from_template`, etc.): adapts a real, checked-in-verbatim dashboard JSON from `templates/` (fetched from the project's own GitHub repo or grafana.com — never hand-edited, only the generator adapts it). Before adapting a new grafana.com dashboard, **check its top-level keys for the new Grafana schema v2 shape** (`apiVersion: dashboard.grafana.app/v2`, `kind: Dashboard`, `spec.elements`/`spec.layout` instead of classic `schemaVersion`/`panels[]`/`targets[]`) — every helper in this file assumes the classic model; a v2 dashboard needs an entirely separate code path, not supported today. Reject v2 candidates and prefer a classic-schema alternative (an older grafana.com revision, or the project's own bundled dashboard, which is usually classic-schema).

**Template-import sub-patterns** (a template's panel array shape decides which applies):
- **Flat panel list with `type: "row"` marker panels interspersed** (CoreDNS, Harbor, Velero) — use `_remove_row_and_contents(panels, row_title)` to drop a row and its child panels. Before trusting it on a new template, confirm the row's children are actually contiguous in the array immediately after the row marker (print titles in order) — an early draft of the SeaweedFS import used this helper and was bitten by non-contiguous children (two rows' panels interleaved); its current code handles that template's row removal a different way instead. Flux's template needed no row removal at all — it only nulls out two unwanted histogram targets inside an existing panel via `_replace_exprs_exact`, a different helper entirely.
- **Nested/collapsed rows where each row object itself carries its own `panels: [...]` list** (AWX) — `_remove_row_and_contents` doesn't apply; filter both the outer row list and each row's inner `panels` list directly via list comprehension.

**Datasource-ref handling:** `_fix_datasource_refs(d)` rewrites the standard grafana.com `${DS_PROMETHEUS}` placeholder (bare string or `{"uid": "${DS_...}"}` dict shape) to this repo's real datasource (`PROM = {"uid": "grafanacloud-prom", "type": "prometheus"}`). Some templates use additional non-standard shapes (AWX: literal `"awx_prometheus"` uid, legacy numeric uid, bare `{}`; Harbor: `${datasource}` template-variable uid, literal `"prometheus"` placeholder) — these need a dedicated per-template walker function, but **always call the shared `_fix_datasource_refs` too** if the template also uses the standard `${DS_PROMETHEUS}` shape anywhere (Harbor's template mixes all three shapes — a dedicated walker alone would silently leave any `${DS_PROMETHEUS}` panels unresolved). Grep the generated JSON for leftover `${DS_`/`${datasource}`/literal `"prometheus"` strings after every template-import build to catch this class of miss. Never rewrite Grafana's own built-in annotations datasource (`{"type": "datasource", "uid": "grafana"}` or `{"type": "grafana", "uid": "-- Grafana --"}`) — that's a legitimate, distinct reference, not a stale placeholder.

**Fail loud, don't guess:** when scoping a template's panel exprs to this repo's `cluster=`/`namespace=` labels, raise `ValueError`/`KeyError` if a panel's metric isn't recognized/scoped rather than silently shipping an unadapted query — this pattern has caught real bugs (a Harbor row-removal bug that left an unscoped `harbor_core_*` expr in the output) exactly when it's supposed to.

**Verification checklist, every dashboard change:** `python3 generate_dashboards.py` clean → `git diff --exit-code -- dashboards/` (drift-guard) → `terraform fmt -check -diff` → grep the generated JSON for leftover `${DS_`/`${datasource}`/literal `"prometheus"`-uid strings → live `query_prometheus` check that each new panel's expr actually returns real, non-stale data (a green generator run proves the JSON is well-formed, not that the dashboard shows anything meaningful) → independent dual review (codex-rescue + fable, run separately, not primed with each other's findings) before merge.

### Cardinality-budget discipline

The Grafana Cloud account's real hard enforcement limit is **15,000 active series** (`err-mimir-max-active-series` — confirmed via live `429` remote-write errors during an incident, not documentation) — distinct from and higher than the ~10,000-series billing/included-series figure, which is a separate, softer threshold. This project worked to a **≤9,500 active series** target ceiling (buffer below the hard cap, plus margin for the billing tier), checked via `grafanacloud_instance_active_series` on the `grafanacloud-usage` datasource.

**Live alert:** `grafana_rule_group.active_series_guard` (`terraform/grafana/alerting.tf`, rule `GrafanaCloudActiveSeriesNearLimit`) fires to the `#infrastructure` Slack channel when `max(grafanacloud_instance_active_series)` stays above **13,500 for 6h** — reframed 2026-09-30 (was `>9,000`, framed around the softer 10,000 billing figure) after the Metrics usage audit below settled this repo's baseline at ~11,500-13,300, durably above both the old alert threshold and the ≤9,500 target — an accepted tradeoff, not a regression. The old threshold left this alert permanently `firing` with zero signal value; the new one gives real lead time (1,500-series margin, though the sustained 7-day peak of ~13,071 was already only ~430 below it, so expect occasional firing under normal drift) before the actual 15,000 ingestion-rejection cap. **This alert only guards against slow drift, not a sudden step change** — Mimir enforces the 15,000 cap live and independently, so `for: 6h` only delays the Slack notification, not the rejection itself; a haproxy-ingress-sized surprise (~6,471 series against an estimated low-hundreds, this repo's own precedent) could blow past the cap before this rule ever fires. The two-step-land discipline below is the actual guard against that class of surprise, not this alert.

- **Checkpoint before and after every change that adds scrape targets** — but only trust the reading if the Alloy metrics collector (`alloy-metrics`, the StatefulSet running `annotationAutodiscovery`) has been stable for a real stretch (no recent pod restarts). A crash-looping collector biases the gauge low (it can't complete scrape+remote-write cycles), and recovery after a fix isn't instant even once the collector is healthy again — Mimir's active-series count only clears already-ingested series as they age out as stale, a lag of tens of minutes, not seconds.
- **Two-step land, every new scrape target:** (1) an annotation-only PR enabling scraping, merged and given time for Flux to reconcile plus a real scrape interval; (2) confirm actual live metric names AND their cardinality (`query_prometheus`/`count by (__name__) (...)`) before writing any dashboard builder — never guess metric names or estimate cardinality from documentation alone. A metric family with a "per pre-reserved slot" cardinality shape (e.g. HAProxy Ingress's `haproxy_server_*`, sized by reserved server slots for dynamic scaling, not actual running pods) can be an order of magnitude higher than a naive backend-count estimate — this actually happened enabling haproxy-ingress metrics (~6,471 series added, not the low-hundreds originally estimated, requiring an emergency follow-up `write_relabel_config` drop rule).
- **`write_relabel_config` drop rules** live in each cluster's `grafana-alloy/manifests/release.yml`, under `destinations.grafanaCloudMetrics.metricProcessingRules` — this project's accumulated precedent for dropping a confirmed-zero-consumer metric family. Always confirm zero consumers first (grep every `dashboards/*.json` panel expr and any `grafana_rule_group` alert rule for the metric name) before adding a drop rule.
- **A "zero consumers" check against only this repo's own `dashboards/*.json` files is unsound — verify against the full live surface.** This Grafana Cloud stack has **98 live dashboards total; only 37 are Terraform-managed** (`search_dashboards` + `get_dashboard_panel_queries`, confirmed 2026-09-29). The other 61 include several legacy, hand-imported duplicates of apps this repo also manages (e.g. a generic "Harbor" dashboard and "HAProxy Ingress" dashboard, distinct from `kn-harbor`/`kn-haproxy-ingress`) that directly query metric families a repo-only grep would flag as unused. Always cross-check `search_dashboards`(all pages) + `get_dashboard_panel_queries` (including `templating.list` — a dashboard's *template variable* `label_values(...)` queries reference metric names too, and won't show up in a panel-only grep) before writing a new drop rule, not just this repo's 37.
- **Grafana Cloud's built-in Kubernetes Monitoring integration IS installed on this stack** — a prior version of this doc claimed it wasn't; that claim was never actually checked against the Grafana Cloud API (no Viewer-level MCP token access existed at the time). It shows up as the `integrations-kubernetes` Grafana folder, holding the standard kubernetes-mixin alert/recording rule set (124 rules — `alerting_manage_rules list` with that `folder_uid`, or `datasource_uid` set to `grafanacloud-prom` for datasource-managed/recording rules). Any future "zero consumers" audit must check this rule set too (`alerting_manage_rules get` per rule to see the actual PromQL `expr` — the `list` operation only returns rule metadata, not query bodies). **Known pre-existing gap surfaced by the 2026-09-29 audit, not yet fixed:** `KubeCPUOvercommit`/`KubeMemoryOvercommit` are both confirmed live at `"Normal (NoData)"` because they transitively depend on `kube_pod_container_resource_requests` (via `namespace_cpu/memory:kube_pod_container_resource_requests:sum` recording rules in the same rule group), which this file's own "Systematic audit" `write_relabel_config` rule already drops. Restoring just `kube_pod_container_resource_requests` (not `_limits`, which neither alert needs) would cost an estimated ≤510 series (~2/container × 255 live containers, both clusters, upper bound — not live-measured since the metric is currently suppressed). Left dropped deliberately pending a product decision on whether these alerts matter enough to pay for. `KubeCPUQuotaOvercommit`/`KubeMemoryQuotaOvercommit` are separately NoData for an unrelated reason (they depend on `kube_resourcequota`, unaffected by any drop rule here — likely just zero because no `ResourceQuota` objects exist on either cluster, a Kubernetes object-provisioning question, not a metrics one).

### Metrics usage audit (2026-09-29)

Follow-up to the 2026-08-31 template-import audit above, prompted by a request to find missing container/pod resource metrics and confirm-then-drop unused ones within the cardinality budget.

**Added:** `clusterMetrics.kubeletResource.metricsTuning.includeMetrics` (both clusters) now lists `container_cpu_usage_seconds_total`/`container_memory_working_set_bytes` — the already-enabled `kubeletResource` feature (job `integrations/kubernetes/resources`, kubelet's `/metrics/resource` endpoint, the Kubernetes resource-metrics API / KEP-1867) exposes these container-scoped series too, just filtered out by the chart's default allow-list; `includeMetrics` is additive to `useDefaultAllowList` (confirmed via actual `helm template` render against the resolved chart version, not just values.yaml comments — the two name sets land in a single combined keep-regex). Deliberately **not** cAdvisor (`clusterMetrics.cadvisor.enabled`) — smaller blast radius (no new scrape job, no new label churn), and `resource_row()` in `generate_dashboards.py` has no `job=` matcher so it works with either collector. cAdvisor remains the fallback only if kubelet's `/metrics/resource` output turns out not to carry `container=`/`pod=`/`namespace=` labels shaped as expected (confirm via `query_prometheus` post-land — same two-step-land discipline as any other scrape addition here). `kubelet.enabled`/`cadvisor.enabled` stay `false`. Network metrics (`container_network_*_bytes_total`, needed by `reliability_row()`) are **not** exposed by kubelet's `/metrics/resource` endpoint — wiring those up is a separate, later decision that would need cAdvisor's own, larger cardinality cost; not folded into this change.

**Dropped (confirmed zero consumers across all 98 live dashboards + kubernetes-mixin alert/recording rules + this repo's 37):** `haproxy_backend_agg_(check_status|server_status|server_check_status)` (kubenuc only, ~1,092 series), 9 unused `haproxy_backend_*` sub-metrics (kubenuc only, ~405 series), `SeaweedFS_s3_lifecycle_dispatch_limiter_wait_seconds_bucket` (kubenuc only, ~48 series — distinct from the sibling `SeaweedFS_filerStore_request_seconds_bucket`, which `kn-s3.json` does use), `certmanager_http_acme_client_request_duration_seconds_bucket` (both clusters, ~69 series — `_sum`/`_count` retained per convention), `coredns_kubernetes_dns_programming_duration_seconds_bucket` (both, ~63 series), `promhttp_metric_handler_requests_total` (both, ~61 series), `controller_runtime_webhook_latency_seconds_bucket` (both, ~52 series), `cloudflared_rpc_client_latency_secs_bucket` (both, ~54 series). Combined confirmed-safe total: ~1,844 series (~1,728 kubenuc, ~116 k8s-vms-daniele) — `release.yml`'s drop-rule comments were shortened to one line each in 2026-10 (chore(grafana-alloy): shorten drop-rule comments, move detail to Confluence); see [Confluence: Grafana Alloy](https://fastnetserv.atlassian.net/wiki/spaces/IT/pages/748257281) for the exact per-metric counts and consumer-check basis.

**Considered and rejected as drop candidates** (would have been false positives from name-pattern matching alone): `rest_client_requests_total` (100 series — used by `flux.json`, both clusters), `authentik_policies_execution_time_bucket`/`_sum` (105 series — used by `kn-sso`, easily confused with the already-dropped `authentik_policies_engine_time_total_seconds_bucket`), `kube_node_status_allocatable`/`kube_node_status_capacity` (108 series — no consumer in this repo's 37 dashboards, but a real, confirmed consumer of `KubeCPUOvercommit`/`KubeMemoryOvercommit`, see above).

**Gap to the ≤9,500 target:** at audit time, active series stood at ~12,862 (kubenuc ~10,227 / k8s-vms-daniele ~2,578); ~1,844 confirmed-safe series covers roughly half the ~3,900-series reclaim the target implied. The hard 15,000 ceiling is not at risk either way (12,862 + ~510 for the `kubeletResource` addition ≈ 13,372). Remaining, larger, not-yet-actioned levers (each is a bigger decision, deliberately not taken this round):
- Retiring the legacy generic Harbor dashboards (queries the `registry_*_bucket`/`harbor_task_*`/`harbor_core_*` families, ~908+ series) or the legacy generic "HAProxy Ingress" dashboard (keeps the `haproxy_backend_*`/`frontend_*` aggregates alive) — either would need a diff against what `kn-harbor.json`/`kn-haproxy-ingress.json` independently consume before finalizing a number, and retiring a dashboard someone might still be viewing is a product decision, not a metrics one.
- `kube_pod_status_phase` (865 series, ~5 per pod) — a label-value-scoped drop on phase values no consuming dashboard actually needs (e.g. `Succeeded`/`Unknown`) could reclaim a few hundred series; not checked which of the 18 consuming dashboards need which phase values.

**Follow-up (2026-09-30): `status_row()`'s "Ready Containers" panel was separately broken, unrelated to the above.** `kube_pod_container_status_ready` was never in this chart's own kube-state-metrics default allow-list (`default-allow-lists/kube-state-metrics.yaml` — confirmed against the resolved 4.5.2 chart) — the dashboard builder has queried a metric name that was never enabled by the chart's default config, since before this repo's cardinality-budget work even started. Not a drop-rule casualty. Fixed the same way as the `kubeletResource` addition above: `clusterMetrics.kube-state-metrics.metricsTuning.includeMetrics: [kube_pod_container_status_ready]` (both clusters) — confirmed additive via `helm template`, same mechanism as `kubeletResource.metricsTuning.includeMetrics`. Cost is cheap (~1 series/container, same shape as the already-live `kube_pod_container_status_restarts_total`, ~255 series total). Live-confirmed post-merge at exactly 255 series (177 kubenuc + 78 k8s-vms-daniele).

**Follow-up (2026-09-30): cAdvisor enabled, scoped to `container_network_*_bytes_total` only, for `reliability_row()`'s "Network I/O" panel.** `clusterMetrics.cadvisor.enabled: true` (both clusters) with `metricsTuning.useDefaultAllowList: false` + `includeMetrics: [container_network_receive_bytes_total, container_network_transmit_bytes_total]` — deliberately not the chart's ~19-family cadvisor default allow-list, confirmed via `helm template` that the resulting keep-regex only matches these two names. `nodeAddressFormat` stays at the chart default (`direct`), same as `kubeletResource`, already proven live to need no `nodes/proxy` RBAC. **A real gotcha caught before landing, not after:** the chart's own `dropEmptyImageLabels` default (`true`) drops any `container_(cpu|fs|memory|network|pressure)_*` series with an empty `image` label — a guard against a known cAdvisor duplicate-series bug (`google/cadvisor#2688`) — but cAdvisor's network stats are pod-scoped, not container-scoped, and are commonly emitted with an empty `image` label as a matter of course. Since this config includes no cpu/fs/memory/pressure metrics from cadvisor at all, that rule's protective purpose doesn't apply, and leaving it at its default would have risked silently dropping every series this change exists to add — set `dropEmptyImageLabels: false`, confirmed via `helm template` that this removes exactly that one rule block and nothing else. `keepPhysicalNetworkDevices` left at the chart default (`["en[ospx][0-9].*", "wlan[0-9].*", "eth[0-9].*"]`) — filters out `lo`/`veth`/`cni0` noise, a cardinality win, not a restriction. Cardinality is genuinely unestimated pending a live check (two-step land, same discipline as every other scrape addition here — the haproxy-ingress incident, est. low-hundreds vs. actual ~6,471, is the standing reason not to trust an estimate over `query_prometheus`).

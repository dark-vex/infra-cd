# awx-ee — execution environment for the AWX Zabbix job templates (CODE-123)

Built by `.github/workflows/build-awx-ee.yml` into `ghcr.io/dark-vex/infra-cd-ee` (tag `sha-<12>`, referenced **by digest**). The AWX bootstrap registers it; a new digest reaches AWX only when `ansible/awx-zabbix-bootstrap` is re-run.

- **Why custom**: AWX's stock EE ships an old ansible-core; the roles are verified on the workstation's 2.21.x, so the same core and the same collection versions are pinned here.
- **Baked-in env**: `ANSIBLE_VARS_ENABLED` (SOPS vars plugin) and `ANSIBLE_INVENTORY_UNPARSED_FAILED=true`. AWX ignores each role's `ansible.cfg` and rejects `ANSIBLE_*` names from credential injectors, so they must live in the image. The setting is `..._UNPARSED_FAILED`; `..._UNPARSED_IS_FAILED` is silently ignored.
- **sops**: version tracked by Renovate together with `docker/agents/ansible/Dockerfile`; the per-arch sha256 values are refreshed from the release's `sops-vX.checksums.txt` by a Renovate postUpgradeTask (`.github/scripts/update_sops_checksums.sh`), and the `sops-checksum` PR guard re-verifies them, cosign signature included.
- **Base image and the CPU baseline (do not move to Stream 10)**: the base is CentOS **Stream 9** with Python 3.12 installed next to the default 3.9 (ansible-core 2.21 needs 3.12). A first build on Stream 10 passed CI and died in AWX with `Fatal glibc error: CPU does not support x86-64-v3`: RHEL 10 / Stream 10 need the x86-64-v3 baseline, the AWX workers' vCPU does not have it, and GitHub's runners do, so CI cannot catch it. Stream 9 is x86-64-v2, like the stock awx-ee that already runs there. Check the worker CPU flags (`lscpu`) before changing the base.
- **What is pinned, and what is not**: pinned are the base image (by digest), ansible-core, ansible-runner, ansible-builder, the collections, `sops` (version and checksum) and the three direct Python dependencies in `requirements.txt` (versions of the image that runs in AWX). **Not pinned**: the transitive Python dependencies and the OS packages are resolved at build time, so two builds of the same commit can differ. This image holds the age key and the SSH key during a job, so the next step is a constraints file for the whole dependency tree (a `pip freeze` of the tested image, applied with `PIP_CONSTRAINT` in the builder stage); ansible-builder merges every collection's own requirements into one file, so `--require-hashes` cannot simply be switched on.
- **Workflow permissions**: the `test` job (pull requests and pushes) is read-only; only the `publish` job, which never runs for a pull request, has `packages: write`. It rebuilds and smoke-tests again before pushing, so it pushes the image it tested. Checkout does not persist the token.
- **Smoke test guards**: it fails if the base is not Stream 9, and if `ansible.utils.ipaddr` is missing (the `zabbix-agent` guard validates the address override with it). Renovate is also told it may only move the digest of `stream9` (`.renovate/versioning.json5`).
- **GHCR visibility**: a new package starts private. Make it public once (nothing secret inside); the workflow's anonymous-pull step fails until you do.
- **Local test** (arm64 or amd64): `ansible-builder build -f execution-environment.yml -t infra-cd-ee:local --container-runtime docker`, then run `smoke-test.sh` in it as the workflow does.
